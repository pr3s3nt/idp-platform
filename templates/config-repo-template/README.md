# `<app>-config` — generated deployment manifests

> **Do not edit `manifests.yaml` by hand.** The orchestrator overwrites both files on
> every deploy, so manual edits are silently lost on the next push.

This repo is the handoff point between the platform's orchestrator and Fleet:

```
<app>-config/
├── staging/
│   ├── fleet.yaml        # Fleet Bundle -> namespace <app>-staging
│   └── manifests.yaml    # GENERATED by the orchestrator
├── prod/
│   ├── fleet.yaml        # Fleet Bundle -> namespace <app>-prod
│   └── manifests.yaml    # GENERATED by the orchestrator
└── README.md
```

Fleet discovers `staging/` and `prod/` as two independent Bundles from this single
GitRepo, so either environment can be paused or rolled back on its own in Rancher.

## How to change something

| You want to change | Where to change it |
|---|---|
| The app itself (ports, env vars, resources it claims) | `score.yaml` in the **app** repo |
| Replicas, CPU/memory, env labels | `patches/{staging,prod}.tpl` in the **idp** repo |
| How a resource (dns, route, postgres) is realised | `provisioners/local.provisioners.yaml` in the **idp** repo |
| Which catalog version this app renders against | `platform.lock` in the **app** repo |

## Secrets

Generated secrets (for example a Postgres password) are **not** in this repo by design.
The orchestrator applies them straight to the cluster namespace with `kubectl create`
— create-if-missing, so re-running a deploy never rotates a live database password.
Manifests here reference them via `secretKeyRef`.

## Promoting to prod

`staging/` updates on every push to the app's main branch. `prod/` is only bootstrapped
once and thereafter moves via an explicit `promote-request` dispatch — either `tag-only`
(retag the existing manifest) or `re-render` (rebuild from the tagged commit using the
catalog version that commit pinned).
